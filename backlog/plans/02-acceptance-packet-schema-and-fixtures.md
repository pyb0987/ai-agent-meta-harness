# Plan 02: AcceptancePacket Schema and Fixtures

## Purpose

Define the first concrete v2 `AcceptancePacket` schema and example packets before
implementing the packet checker or CLI.

Plan 01 made the v1 archive boundary honest. Plan 02 defines the packet evidence
shape that will later replace bootstrap notes, broad `Multi-review not required:`
dispositions, and CLI-only archive waiver provenance.

## Success Criteria

- The public packet surface remains `meta`, `input`, and `result`.
- The fixture set covers at least:
  - start packet
  - finalized routine work
  - finalized harness-affecting work
  - finalized waiver or downgrade
  - blocked packet
- Packet examples preserve Meta-Harness essentials:
  fixed evaluator boundary, trace reuse, confounder isolation, evidence honesty,
  and human judgment provenance.
- Fixtures distinguish generated fields from human-provided inputs.
- No fixture requires users to hand-author inferred change class, required
  evidence, required review, or final eligibility.
- The plan does not implement `governance start`, `finalize`, or `check`; it only
  fixes the target shape for the next implementation plan.

## Scope

In scope:

- `backlog/fixtures/acceptance-packets/`
- `backlog/v2-roadmap.md`
- `MAINTENANCE.md` only if the packet boundary needs a concise update
- tests that prevent packet examples from drifting away from the v2 public shape

Out of scope:

- Implementing `scripts/check-governance-acceptance.py`
- Replacing release gates or pre-commit hooks
- Migrating v1 backlog records into packet form
- Adding a durable packet archive validator

## Minimal Packet Shape

```yaml
AcceptancePacket:
  meta:
    packet_id: string
    schema_version: string
    lifecycle: start|finalized|blocked
    mode: staged|base-ref|worktree
    created_at: YYYY-MM-DD
    finalized_at: YYYY-MM-DD|null
  input:
    intent: string
    actor: string
    source_refs: []
    user_judgment: {}
  result:
    inference: {}
    evidence: {}
    judgment: {}
    decision: {}
```

### `meta`

`meta` identifies the packet and its lifecycle. It is generated by the harness
except for explicit output path or mode choices passed to CLI commands.

Required fields:

- `packet_id`
- `schema_version`
- `lifecycle`
- `mode`
- `created_at`
- `finalized_at`

### `input`

`input` records human or caller-provided material. Humans provide intent and
judgment facts; they do not classify the change manually unless they are
requesting an exception.

Required fields:

- `intent`
- `actor`
- `source_refs`
- `user_judgment`

`user_judgment` may include waiver, downgrade, skipped-evidence, or residual-risk
requests. Each such entry must carry actor, role, date, reason, and source ref.
Waiver and downgrade requests must also name the required evidence or required
review item they affect; broad untargeted bypasses are not valid packet input.

### `result`

`result` is generated by the harness during finalization.

Required groups:

- `inference`: change class, impact, touched paths, protected boundary changes,
  intended scope, actual scope, deviations, isolation status, required evidence,
  required review, and eligibility prerequisites.
- `evidence`: command results, search-set before/after refs, raw artifact refs,
  source refs, and skipped evidence. Packet hash material is deferred to the
  packet archive integration plan.
- `judgment`: review scores, VETO handling, waivers, downgrades,
  residual-risk acceptance, and why-not-10 dispositions.
- `decision`: accepted/blocked state, stable-handoff eligibility, reason, and
  next action.

## Design Rules

- Keep the public surface to `meta`, `input`, and `result`.
- Put computed details under `result`, not beside the public sections.
- Treat `Multi-review not required` as a generated downgrade/waiver decision, not
  a free-form bypass.
- Require every waiver or downgrade to target an inferred required evidence or
  required review item.
- Store archive waiver provenance in packet judgment/evidence before accepted
  post-import archive edits are allowed.
- Treat `worktree` packets as exploratory. Worktree packets are always
  non-stable-handoff-eligible in v2.0 fixtures.
- Use source refs rather than long embedded logs whenever raw artifacts already
  exist in repository traces, CI logs, screenshots, exported traces, or packet
  artifacts.

## Multi-Review Requirements

Before accepting this plan, run multi-review with at least these critic scopes:

- schema minimality: confirms the three-section public surface remains simple and
  does not revive v1 human-authored gates.
- methodology coverage: confirms fixed evaluator, trace reuse, confounder
  isolation, evidence honesty, and human judgment provenance are represented.
- implementation readiness: confirms the fixture set is enough for the next
  checker/CLI plan without smuggling implementation decisions into examples.

All required critic scores must be at least 9. Any VETO requires updating the
plan or fixtures and rerunning the affected critic. Every score 9 must record a
why-not-10 reason and residual-risk or follow-up disposition.

## Open Questions

- Whether `actor` should be a string in v2.0 fixtures or a structured object with
  name, role, and tool/runtime.
- Whether `source_refs` should be normalized as strings first, then promoted to
  objects once the checker resolves them.
